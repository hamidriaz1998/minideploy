# Server Layout

This document describes the file system layout on the server, how releases are named, and how state is managed.

## Directory Structure

```
/opt/<app_name>/                  # App-specific deploy path
├── upload/                       # rsync target (mutable)
├── releases/                     # Immutable release snapshots
│   ├── 20260603-143022/          # Timestamped release
│   │   ├── app                   # Build artifact
│   │   └── static/               # Directory artifact
│   └── 20260602-120000/
│       ├── app
│       └── static/
└── current → releases/20260603-143022/   # Active symlink

/var/lib/minideploy/              # Daemon state directory
├── minideploy.db                 # SQLite database (all state)
├── state.json.migrated           # Previous JSON state (if migrated)
└── daemon.log                    # Daemon logs
```

## Directory Permissions

| Path | Owner | Purpose |
|---|---|---|
| `/opt/<app>/` | `minideploy:minideploy` | App deploy data |
| `/opt/<app>/upload/` | `minideploy:minideploy` | rsync target |
| `/opt/<app>/releases/` | `minideploy:minideploy` | Release snapshots |
| `/var/lib/minideploy/` | `minideploy:minideploy` | Daemon state |
| `/usr/local/bin/minideploy` | `root:root` | Daemon binary |

The `minideploy` user owns all deploy paths so the daemon can read, write, and symlink without sudo.

## Release Naming

### Auto-Generated Names

Releases are named by timestamp in the format `YYYYMMDD-HHMMSS`:

```
20260603-143022
││││││ ││││││
││││││ │││││└─ second (22)
││││││ ││││└─── minute (30)
││││││ │││└──── hour (14)
││││││ ││└────── day (03)
││││││ │└─────── month (06)
││││││ └──────── year (2026)
│││││└────────── (generated by daemon)
```

This ensures:
- **Sortable** alphabetically (newer > older)
- **No collisions** (two deploys in the same second are possible but virtually impossible in practice)
- **Human-readable** (you know when each release was made)

### Custom Names

You can override the release name with the `--release` flag:

```bash
minideploy deploy --release v2.1.0
```

Custom names are stored as-is. They must be valid directory names (no `/`, null bytes, etc.).

## SQLite Database

The daemon persists all state to `/var/lib/minideploy/minideploy.db` using SQLite.

### Migration from JSON

If you're upgrading from a version that used `state.json`, the daemon automatically migrates your data on first startup:

1. Detects `state.json` in the state directory
2. Reads all apps, releases, instances, and API keys
3. Inserts them into the SQLite database
4. Renames `state.json` to `state.json.migrated` (backup)
5. Continues with SQLite

The migration is safe and non-destructive — your old state is preserved as `.migrated`.

### Database Schema

```sql
meta         (key, value)              — daemon_version, metadata
api_keys     (id, key_hash, created_at)
apps         (id, name, service_type, service_name, deploy_path, created_at)
instances    (id, app_id, instance_id, port, env_json)
releases     (id, app_id, name, created_at, is_current)
```

### Write Safety

SQLite provides transactional safety with WAL (Write-Ahead Logging) mode:
- Partial writes cannot corrupt the database
- Concurrent reads during writes
- Atomic transactions via `BEGIN` / `COMMIT`
- Automatic crash recovery on next open

## rsync and the Upload Directory

The `upload/` directory is the only mutable directory. Its purpose is to give rsync a stable target for incremental transfers.

### How rsync Uses It

```bash
# First deploy: uploads everything
rsync -avz --delete app frontend/build/ root@vps:/opt/my-api/upload/

# Second deploy: only changed files
rsync -avz --delete app frontend/build/ root@vps:/opt/my-api/upload/
# app changed → only app transferred, frontend/build/ is cached
```

### What Happens on Deploy

```
Before deploy:
  upload/ has app (v2)
  releases/20260602/ has app (v1)
  current → releases/20260602/

Deploy triggered:
  1. Daemon copies upload/ → releases/20260603/ (complete copy)
  2. Daemon swaps symlink: current → releases/20260603/
  3. Daemon restarts instances

After deploy:
  upload/ has app (v2) — unchanged
  releases/20260603/ has app (v2) — the new active release
  current → releases/20260603/
```

## Disk Usage Considerations

- **Releases are complete copies**: Each release is a full copy of `upload/`. For large apps with many releases, disk usage grows linearly.
- **Releases are not compressed**: Files are stored as-is.
- **No automatic cleanup**: Old releases accumulate. Use destroy (hard) to remove everything, or manually clean up `releases/` on the server.

### Estimating Disk Usage

```bash
# Check app disk usage
du -sh /opt/my-app/

# List release sizes
du -sh /opt/my-app/releases/*

# Manual cleanup (keep only the last N releases)
cd /opt/my-app/releases && ls -t | tail -n +5 | xargs rm -rf
```
